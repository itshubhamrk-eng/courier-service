# ADR-001 — Multi-Tenancy Strategy: Shared Database, Shared Schema

- **Status:** Accepted
- **Date:** 2026-07-22
- **Deciders:** Backend lead
- **Supersedes:** —
- **Amended:** 2026-07-29 — see *Amendment* at the end. The strategy is unchanged; the
  vocabulary is. There is no separate tenant: a company is the owner.
- **Amended again:** 2026-07-30 — the physical `tenant_id` column, deferred in the first
  amendment, is now `company_id`. See *Amendment* point 1, updated below, and
  `MEMORY/CHANGELOG.md`.

## Context

The platform serves many independent courier companies from one deployment. Every
row of business data belongs to exactly one tenant, and a cross-tenant read is a
Sev-1 incident. We must choose how tenant data is physically separated.

Expected shape of the business, which drives the decision:

- Hundreds to low thousands of tenants, most of them small.
- Tenants share an identical schema; no per-tenant customisation of tables.
- A small team operates the platform. Migration effort scales with the number of
  physical schemas.
- Cost sensitivity is high at the current stage; per-tenant infrastructure is not
  affordable.

## Options Considered

### A. Database per tenant
Strongest isolation. Trivial per-tenant backup/restore and "delete my data".
Rejected: N connection pools, N migration runs, expensive at thousands of tenants,
and slow tenant provisioning. Operationally disproportionate for our team size.

### B. Schema per tenant (shared database)
Good isolation, single server. Rejected: MySQL has no cheap cross-schema query
path for platform-wide analytics, the connection pool must be re-pointed per
request, and Flyway must iterate every schema on deploy — a migration failure
halfway through leaves the estate inconsistent.

### C. Shared database, shared schema, discriminator column  ← **chosen**
One schema, every tenant-owned table carries `tenant_id`. Isolation is enforced
in the persistence layer rather than by physical separation.

## Decision

**Option C.** One database, one schema, a `tenant_id BINARY(16) NOT NULL`
discriminator on every tenant-owned table, with isolation enforced automatically
by Hibernate rather than by developer discipline.

Implementation contract:

1. Tenant-owned entities extend `TenantAwareEntity`, which declares
   `@FilterDef(name = "tenantFilter", parameters = @ParamDef(name = "tenantId", type = UUID.class))`
   and `@Filter(name = "tenantFilter", condition = "tenant_id = :tenantId")`.
2. `TenantFilterAspect` enables the filter on the Hibernate `Session` for every
   request, using `TenantContext.getTenantId()`.
3. `TenantEntityListener` stamps `tenant_id` on `@PrePersist` and throws
   `TenantViolationException` if an update targets another tenant's row.
4. `TenantContext` is a `ThreadLocal`, populated by `TenantResolutionFilter` from the
   **verified JWT** `tid` claim and cleared in a `finally` block.
5. `X-Tenant-ID` is honoured only for `PLATFORM_ADMIN`, and every use is
   written to `audit_logs`.
6. `tenant_id` is the **leading column** of every composite index, and every
   unique constraint is scoped by it — `UNIQUE (tenant_id, awb_number)`, never
   `UNIQUE (awb_number)`.
7. Platform-level tables (`tenants`, `audit_logs`) extend plain `BaseEntity` and
   are intentionally outside the filter.

## Consequences

### Positive
- One migration run, one connection pool, one set of dashboards.
- Instant tenant provisioning — an insert, not a `CREATE DATABASE`.
- Cross-tenant platform analytics is a plain SQL query.
- Cheapest option per tenant by a wide margin.

### Negative / Risks
- **Isolation is code-enforced, not physical.** One forgotten filter leaks data.
  Mitigation: no feature code may write raw `tenant_id` predicates or disable the
  filter; every tenant-aware repository ships with a cross-tenant leak test
  (see `BACKLOG.md` → Cross-Cutting).
- **Native queries bypass Hibernate filters.** Mitigation: `@Query(nativeQuery = true)`
  is banned in tenant-aware repositories without an explicit reviewed exception.
- **Noisy-neighbour** — one large tenant can degrade shared resources.
  Mitigation: per-tenant rate limiting; large tenants can be migrated to their own
  database later (the discriminator makes extraction a filtered dump).
- **"Delete my tenant's data"** is a `DELETE ... WHERE tenant_id = ?` across many
  tables rather than a `DROP DATABASE`. Mitigation: a scripted, tested purge job.
- **Backup/restore granularity** is all-or-nothing. Per-tenant point-in-time
  restore requires selective export tooling — not built yet, accepted.

## Revisit When

- A single tenant exceeds ~20% of total row volume or IO.
- A regulated customer contractually requires physical data separation.
- Cross-tenant leak incidents occur despite the test suite.

The chosen design keeps the exit open: because `tenant_id` is on every row, moving
a tenant to Option A is a filtered export plus a routing change, not a rewrite.

## Amendment — 2026-07-29: a company is the owner, and some rows have no company

Two changes, neither of which alters the decision above.

### 1. The word "tenant" is gone from the code

`TenantContext` → `CompanyContext`, `TenantAwareEntity` → `CompanyOwnedEntity` (field
`tenantId` → `companyId`), filter `tenantFilter` → `companyFilter`, header `X-Tenant-ID` →
`X-Company-ID`, JWT claim `tid` → `cid`. The mechanism is identical; the product only ever
had one word for this thing and now the code does too.

**The physical column was `tenant_id`, until 2026-07-30.** Renaming it across the ~28
company-owned tables was deferred at first, then done as its own migration set: Java and
MySQL both say `company_id` now, joined in one place — `@Column(name = "company_id")` on
`CompanyOwnedEntity`. Index and unique-key names carry `_company_` to match. Detail,
including a pre-existing bug in `V12` this rename surfaced, is in `MEMORY/CHANGELOG.md`.

**A new company-owned table is created with a `company_id` column directly** — the
transitional "still create it as `tenant_id`" guidance is retired along with the column
it protected.

### 2. Some rows belong to the platform, not to a company

The six geography master lists — country, state, district, city, area, pincode — are one
catalogue shared by every company. Per-company geography meant `PUNE` was a different row
in each company, so no rate card, serviceability check or report could be compared across
two of them.

They remain `CompanyOwnedEntity` subclasses. Their rows carry the reserved owner
`GlobalMasters.PLATFORM_COMPANY_ID` (`00000000-0000-0000-0000-000000000001`), and the
Hibernate filter still applies to every read and write.

That last point is the reason for the design rather than an accident of it:

- `(tenant_id, code)` was already unique, so one owner makes it a **global** unique on
  code with no schema change.
- The filter stays on. A code path that forgets to bind the platform id returns
  **nothing**, which is a visible bug, rather than **everything**, which is a leak.
- The constant is deliberately not a valid time-ordered UUID, so it can never collide with
  a generated `companyId` and is recognisable on sight in a row nobody expected.

The alternative — a second entity hierarchy with no owner column — would have duplicated
the shared head, repository, specification and abstract service that let one implementation
serve all twelve master lists, because Java has one superclass. That machinery is worth
more than the column.

**The escape hatch is still not general.** Feature code cannot disable the filter; it can
only bind a different owner through `CompanyContext.runAs(...)`, which restores the
previous binding afterwards. `AbstractMasterDataService.withOwner(...)` is the only caller
that does so routinely, and it does so on the write path as well as the read — a global
row created under a super admin's own binding would silently belong to their home company.
